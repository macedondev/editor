## 1. TL;DR

flutter_monaco 3.0 is a ground-up rebuild of the package's spine while keeping its hardest-won assets intact:

- **One wire protocol.** Today there are three ways Dart talks to Monaco (an envelope, two error-swallowing eval helpers, and raw script strings) with three different error contracts. V3 has exactly one: a versioned, request-correlated, channel-based protocol that behaves identically on Android, iOS, macOS, Windows, and Web. Every failure is a typed `MonacoException`. Nothing is silently defaulted.
- **JavaScript becomes real files.** The ~1,950 lines of JavaScript currently embedded in a Dart string in `monaco_assets.dart` move verbatim into `assets/monaco/bridge/*.js`. Dart-string escaping bugs (the `\\n` worker-shim class of bug) become impossible. The manual `htmlGenerationVersion` cache-bust constant is deleted; staleness is engineered away instead of versioned around.
- **Editor is born configured.** A two-phase boot (page ready -> boot command with options/text/theme -> editor ready) replaces "create editor with hardcoded markdown/vs-dark, then patch it from Dart". The wrong-theme flash, the pre-ready content queues, and the widget's double option application all disappear.
- **Document/editor split, like Monaco itself.** `MonacoController` sheds its god-object status: text/model operations live on `MonacoDocument` handles (mirroring Monaco's `ITextModel`), editor-level operations stay on the controller (mirroring `ICodeEditor`). Multi-document support becomes real instead of Uri-string plumbing.
- **Open sets become open types.** `MonacoTheme`, `MonacoLanguage`, and `MonacoAction` become zero-cost Dart extension types over `String` with const built-in catalogs. Custom themes, contributed languages, and arbitrary command ids are first-class; `EditorOptions.themeId` and its `effectiveThemeId` workaround are deleted. Dart 3.10+ dot shorthand (`executeAction(.formatDocument)`) works out of the box.
- **Options that tell the truth.** All `EditorOptions` fields become nullable; null means "not specified" and is omitted from the payload, so `updateOptions(EditorOptions(fontSize: 16))` finally means "change the font size" instead of "reset 40 fields to package defaults". Structured sub-options (`minimap`, `padding`, `scrollbar`, `guides`, `stickyScroll`) plus an `extra` map cover the entire Monaco option surface without waiting for package releases.
- **Two headline features:** Dart-defined editor actions with keybindings (`controller.addAction`), and a `MonacoDiffEditor` widget (severable to 3.1 if needed).
- **Kept as-is by design:** the entire LSP subsystem (2.3.0, excellent), the scroll handoff feature, the focus engineering (macOS first-responder plugin, Windows WebView2 focus, mobile tap bridges), the web overlay shield family, and `MonacoEditorTheme`.

## 2. Where 2.3.0 stands - audit findings

Everything below is verified against the current sources. File references are to the 2.3.0 tree.

### 2.1 The protocol is three protocols

`MonacoController` reaches JavaScript four different ways:

| Path | Used by | Error contract |
|---|---|---|
| `_invokeMonacoCommand` -> `window.flutterMonacoInvoke` (sync envelope via `runJavaScriptReturningResult` + triple JSON decode) | setValue, setTheme, applyEdits, markers, ... | throws `MonacoJavaScriptException` |
| `_executeJavaScript` / `_executeJavaScriptWithJson` (raw eval, `convert_object` coercion) | getSelection, findMatches, saveViewState, createModel, ... | catches everything, `debugPrint`, returns `defaultValue` |
| raw `runJavaScript` with hand-built script strings | revealLine, setModel, restoreViewState, scrollToTop, focus, completion responses | platform exception or nothing |
| `flutterMonacoInvokeAsync` + `invokeResult` channel event (request-id correlated) | LSP only | typed, correlated, cross-platform-identical |

Consequences, concretely:

- `getValue()` returns `''` on bridge failure (`monaco_controller.dart:1164`). An app cannot distinguish "empty document" from "bridge died", which for a code editor is a data-loss hazard.
- `EditorState.theme` is always `null` (`monaco_controller.dart:1653`) because `getEditorState` never asks for it, and issues five sequential round trips for one snapshot.
- Windows result strings need `parseWindowsScriptResult`; iOS/macOS/Android/Web each decode differently; `_decodeJavaScriptEvaluationResult` runs a triple `jsonDecode` loop to cope.
- The LSP comment in `monaco_assets.dart:733-742` states the fix outright: the channel-correlated path "behaves identically on Android, iOS, macOS, Windows, and Web because no platform has to unwrap a JS Promise". V3 makes that path the only path.

### 2.2 The JavaScript lives inside a Dart string

`MonacoAssets.generateIndexHtml` (`monaco_assets.dart:334-2418`) is ~1,950 lines of JavaScript inside a Dart string literal:

- No syntax checking, no linting, no editor tooling; a comment at `monaco_assets.dart:428-431` documents an actual shipped bug class ("the newline escapes must be written as `\\n` ... which is a SyntaxError ... workers then fall back to the main thread").
- Cache staleness is managed by hand: `htmlGenerationVersion` ("Bump this whenever ... the JS bridge changes", `monaco_assets.dart:57-71`). Forgetting the bump ships stale bridges - the "HTML cache gotcha" already bit during 2.3.0 development.
- The editor is created with hardcoded options (`value: '// Monaco Editor is ready', language: 'markdown', theme: 'vs-dark'`, `monaco_assets.dart:2394-2402`), then Dart re-applies the real options after ready. Users see a markdown/vs-dark flash; `MonacoController.create` applies options once and `MonacoEditor._bootstrap` applies them again "to be safe" (`monaco_editor_view.dart:429-436`).

### 2.3 The controller is a god object

`monaco_controller.dart` is 1,904 lines mixing: lifecycle + readiness queues, three JS invocation paths, focus orchestration with per-platform static helpers, content/lines/edits, decorations (one implicit registry per controller), markers (string owners, `clearAllMarkers` hardcodes three of them), find/replace, view state, multi-model ops on raw `Uri`s, a completion provider registry, an LSP manager, and JS escape hatches. Specific defects:

- `getLinesContent` issues one bridge round trip per line (`monaco_controller.dart:1278-1299`).
- `revealLine` does a `getLineCount` round trip for Dart-side validation the JS could do (`monaco_controller.dart:1213-1223`).
- `executeBatch` is a misleading name for a sequential for-loop (`monaco_controller.dart:1630`).
- Pre-ready `setValue`/`setLanguage` maintain a hand-rolled last-write-wins queue with different behavior on web vs native (`monaco_controller.dart:296-309, 1180-1193`); plain awaiting of readiness gives the same last-write-wins ordering for free.
- `MonacoController.create` blocks until ready on native but returns early on web (`monaco_controller.dart:228-232`), so every downstream consumer needs platform-conditional readiness handling.

### 2.4 Models fight the domain

- `EditorOptions` serializes every field always (`toMonacoOptions`, `editor_options.dart:256-299`), so `updateOptions(EditorOptions(fontSize: 16))` silently resets ~40 options to package defaults. Monaco's own `updateOptions` is partial; ours cannot express "just this field".
- Open sets are modeled as closed types: `MonacoTheme` is an enum (custom themes forced the parallel `themeId` field + `effectiveThemeId` getter, `editor_options.dart:34, 162`); `MonacoLanguage` is an 85-entry enum that drifts with each Monaco upgrade and cannot represent contributed languages; `MonacoAction` is a class of ~350 `static const String`s, so `executeAction` takes a raw `String`.
- `LiveStats` bakes UI strings into the model (`({int value, String label})` records with `'Ln'`, `'Sel Ch'` labels) and encodes cursor position as `line * 1000 + column` (`monaco_types.dart:966`).
- Wire parsing is defensively loose everywhere: `Range.fromJson` accepts `startLineNumber` or `startLine` or `start_line` or `from_line` (`monaco_types.dart:110-133`) via `convert_object`. We control both ends of this wire; alternative-key tolerance only hides protocol drift.
- `padding` is `Map<String, int>?`; `minimap`/`wordWrap`/`lineNumbers` are bools where Monaco has richer types.

### 2.5 What is excellent and must survive intact

- **LSP subsystem** (`lsp/`, 2.3.0): transports (WebSocket/bridged/custom), connection state machine with reconnect policy, `LspServerProcess` with stdio framing, the Monaco 0.55.1 client wrapper that adds the missing `dispose()` and the benign-refresh handlers that keep pyright alive. Verified against Monaco sources; do not touch the logic.
- **Focus engineering** (2.0.0-2.2.2): the three-layer focus model (Flutter focus / native focus / DOM focus), macOS first-responder plugin channel, Windows WebView2 `MoveFocus` handling, the `forceFocus` idempotency guard, mobile tap-vs-scroll gesture bridges, Android web focus guards, two-sided web keyboard handoff.
- **Mobile web survival kit** (#11): `touch-action: none` containment, visual-viewport keyboard fit, parent-binding leak prevention.
- **Scroll handoff** (2.3.0): JS edge detection + Dart frame-coalesced application through `ScrollPosition.pointerScroll`.
- **Web overlay stack**: `MonacoWebInteractionCoordinator` (base-enabled + lock set), DOM shield, `MonacoOverlayBoundary`, `MonacoScaffold`, `MonacoFocusGuard`, `MonacoRouteObserver`.
- **Asset pipeline** (extraction, sentinel, `AssetManifest` copy) and **`MonacoEditorTheme`** chrome theming.

## 3. Design principles

1. **One way to do each thing.** One protocol, one error contract, one theme field, one action type. Parallel APIs for the same concept are design bugs.
2. **Mirror Monaco's own architecture.** Monaco splits `ITextModel` (content) from `ICodeEditor` (view). V3 mirrors it: `MonacoDocument` / `MonacoController`. When in doubt, model what Microsoft models.
3. **Make bug classes impossible, not guarded against.** JS in `.js` files kills escaping bugs. Always-rewriting tiny generated files kills stale-cache bugs. Nullable options kill reset-everything bugs. Request-id correlation kills cross-platform decode bugs.
4. **Errors are data, silence is corruption.** Every bridge failure surfaces as a typed exception with the operation name. No `debugPrint`-and-return-default in the library core.
5. **Typed core, open edges.** The typed API covers the curated surface; `extra` options, `runJavaScript`, `LspCustomTransport`, and raw `MonacoAction(id)` keep every Monaco capability reachable without forking the package.
6. **The platform quirks are the product.** The focus/mobile/viewport engineering is the package's real moat. It is ported, never rewritten.

## 6. Wire protocol v3

### 6.1 Envelope

Every JS -> Dart message is a single JSON object:

```jsonc
{ "v": 3, "kind": "<lifecycle|response|event|request|log>", ... }
```

| kind | Shape | Direction / purpose |
|---|---|---|
| `lifecycle` | `{v, kind:'lifecycle', name:'pageReady', protocolVersion:3, monacoVersion:'0.55.1', capabilities:['lsp','diff']}` and `{... name:'ready'}` and `{... name:'fatal', error:{name,message,stack}}` | page loaded / editor created / unrecoverable boot failure |
| `response` | `{v, kind:'response', id:'r12', ok:true, undefined:false, value:<json>}` or `{v, kind:'response', id:'r12', ok:false, error:{name,message,stack}}` | answer to a Dart `dispatch` |
| `event` | `{v, kind:'event', seq:41, name:'contentChanged', data:{...}}` | editor events (see 6.4) |
| `request` | `{v, kind:'request', id:'q7', name:'completion'\|'action', data:{...}}` | JS asks Dart (completion provider, custom action run) |
| `log` | `{v, kind:'log', level:'info'\|'warn'\|'error', message:'...'}` | replaces the `log:` string prefix |

Dart -> JS calls (injected via `runJavaScript`, values JSON-encoded with U+2028/U+2029 escaped exactly as `MonacoLspManager._jsJson` does today):

```js
FlutterMonaco.dispatch({ id: 'r12', method: 'document.getText', params: { uri: null } });
FlutterMonaco.respond({ id: 'q7', ok: true, value: { suggestions: [] } });
```

`dispatch` resolves the dotted method in a registry, runs it through `Promise.resolve(...)`, and always posts exactly one `response` for the id - synchronous and async commands are indistinguishable to Dart. Unknown method, thrown error, and rejected promise all become `ok:false` responses. This generalizes today's `flutterMonacoInvokeAsync` (which is the mechanism the LSP layer already proved on all platforms).

On web, the existing `_flutterToken` stamping and source checks are preserved unchanged; the token rides inside the posted JSON exactly as today.

`seq` on events is monotonically increasing per page; Dart asserts monotonicity in debug mode to catch dropped or reordered messages early.

### 6.2 Handshake and versioning

1. Page loads, `core.js` initializes the registry, posts `lifecycle:pageReady` with `protocolVersion`, `monacoVersion`, `capabilities`.
2. Dart verifies `protocolVersion == 3`; mismatch throws `MonacoProtocolError` through `whenReady` (this can only happen if generated page and Dart code skew, which D03 makes impossible in practice; the check is the belt to that suspenders).
3. Dart dispatches `page.boot` (see command table) with the merged initial options, initial text, language, theme, and scroll handoff sources.
4. JS creates the editor with those options, wires event emitters, posts `lifecycle:ready`.
5. `controller.whenReady` completes; `controller.capabilities` is populated.

The version constant is declared twice on purpose: `const int kMonacoProtocolVersion = 3;` in `lib/src/protocol/envelope.dart` and `const PROTOCOL_VERSION = 3;` in the static asset `core.js`. Dart asserts equality at handshake. Bumping the protocol means changing both files in one commit; the handshake check makes any skew loud instead of silent, and a test (Section 13) pins the two constants together.

### 6.4 Events

| name | data |
|---|---|
| `contentChanged` | `{uri, isFlush:bool, changes:[{range, text}]?, truncated:bool}` - `changes` omitted and `truncated:true` when the summed `text` lengths exceed 65,536 chars (D15) |

### 6.5 JS-to-Dart requests

| name | data | Dart responds with |
|---|---|---|
| `completion` | today's `completionRequest` payload minus the `event` field | `{suggestions:[...], isIncomplete}` (today's `flutterMonaco.complete` payload) via `FlutterMonaco.respond` |
| `action` | `{actionId}` | `{}` after the Dart callback completes (errors return `ok:false`; JS logs and continues) |

Cancellation keeps today's behavior: the JS side resolves with empty suggestions on Monaco cancellation and drops the resolver; a late Dart respond for a dead id is a silent no-op.

### 7.7 Widgets

`MonacoEditor` keeps its 2.3.0 parameter surface with these changes only:

- `options` default stays `const EditorOptions()`; at boot the widget applies `MonacoDefaults.editorOptions.merge(widget.options)` and resolves a null theme from `Theme.of(context).brightness` (D27).
- `initialValue` renamed `initialText` (matches `create`).
- `customCss`/`allowCdnFonts`/`allowedConnectSources` replaced by `page: MonacoPageConfig` (D29). HTML-affecting changes still recreate the controller.
- New `onError: void Function(Object error, StackTrace stackTrace)?` invoked for async command failures the widget itself triggers (replacing silent `_ignoreAsync` debugPrints; when null, errors go to `FlutterError.reportError`).
- `onContentChanged`/`contentDebounce`/`fullTextOnFlushOnly`/`onRawContentChanged` behavior unchanged (pull-model with debounce), now implemented over the typed stream.
- `didUpdateWidget` options diffing: `updateOptions(widget.options)` (sparse; no more full reset), `setTheme` only when the resolved theme changed, `document.setLanguage` only when `options.language` changed.

### 9.2 Behavioral changes

1. Reads throw typed exceptions instead of returning defaults (D06).
2. `create` never blocks on readiness (D05); commands issued before ready are ordered FIFO after ready (this preserves the old queue's last-write-wins outcome for consecutive `setText` calls).
3. `updateOptions` is sparse (D09).
4. No markdown/vs-dark boot flash; the first painted frame uses the requested options (D04).
5. Unknown JS events no longer `debugPrint` as unhandled; they surface as `MonacoUnknownEvent`.
6. `MonacoThemeDefinition.base` is `MonacoBaseTheme` (was `MonacoTheme` enum); `fromJson` maps the same four id strings.
7. `EditorOptions.fromJson` parses only the 3.0 `toJson` shape (strict keys, typed sub-options). It does not read 2.x-era `theme`/`themeId` string blobs; apps that persisted hand-built 2.x option JSON re-serialize once with 3.0 `toJson`.

## 11. Testing strategy

1. **`FakeMonacoHost`** (`test/fakes/fake_monaco_host.dart`): implements the JS side of protocol v3 in Dart. It receives `FlutterMonaco.dispatch(...)` scripts (parsed, not string-matched), routes them through a command-handler map, and posts envelope responses/events through the channel callback. Provides: scripted results per method, error injection, event emission, request emission (completion/action), boot sequencing (`pageReady` -> expect `page.boot` -> `ready`). All controller/document/widget unit tests run against it.
2. **Contract goldens** (`test/protocol/contract_test.dart`): for every command in the 6.3 table, one golden JSON fixture of the dispatch payload and one of a valid response; decoding/encoding round-trips are asserted. This pins the wire so JS and Dart cannot drift silently.
3. **Bridge JS checks** (`test/assets/bridge_syntax_test.dart`): asserts every `bridge/*.js` file exists, is non-empty UTF-8, contains its required registration markers (e.g. `FlutterMonaco.register('document.getText'`), and that `core.js` declares `PROTOCOL_VERSION = 3`. Additionally `tool/check_js.sh` runs `node --check` over each bridge file when `node` is on PATH (CI job; test skips locally when absent).
4. **Widget tests**: port existing `monaco_editor_test.dart`, focus guard, scroll handoff widget tests onto `FakeMonacoHost`.
5. **Existing pure-Dart tests** (LSP framing/transport/types, scroll handoff parsing, options serialization, asset storage) are updated for renames only.
6. **Integration/E2E** (manual gate before release, Section 13): macOS example app; web example (`flutter run -d chrome`); the LSP E2E probe `example/lib/lsp_e2e_probe.dart` on macOS (per its header docs); scroll handoff example on macOS + iOS Safari; Windows smoke test if hardware is available, else note in release PR.
7. **Deleted**: source-scraping tests (`monaco_actions_test.dart` regex over source, `*_source_test.dart` string greps) are replaced by catalog tests iterating the const lists and by the contract goldens.

## 15. Deliberately out of scope for 3.0 (post-3.0 roadmap)

- Linux support (blocked upstream on webview availability; interface already shaped for it).
- Monaco upgrade beyond 0.55.1 (the LSP wrapper is verified against 0.55.1 internals; upgrading is its own change with its own verification pass).
- Push-model content sync (full text pushed from JS on change) - D15's change ranges are the foundation; evaluate after real-world usage.
- Typed wrappers for `executeAction` args payloads.
- Semantic-token / inlay-hint provider registration from Dart (LSP covers the real need today).
- Multiple editors in one WebView (one controller = one WebView remains the model; diff editor is its own instance).
- A `flutter_monaco_test` helper package exposing `FakeMonacoHost` publicly (keep it in `test/` for 3.0; promote if demand appears).
- Performance instrumentation of the protocol (add timing hooks only if a real regression is reported; the LSP layer already proved the channel path at interactive rates).

## 16. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `<script src>` resolution differs per platform (file://, relative, blob-hosted web) | Phase 1 lands extraction alone with manual smoke on macOS + web before any protocol change; URL builders reuse the proven `web_asset_resolver.dart` |
| Behavior drift while porting focus/mobile JS | Verbatim-port rule + Section 14 inventory + manual matrix in Section 13 |
| Protocol migration breaks LSP ordering guarantee (bridged pump needs connect-before-deliver) | `MonacoProtocol.invoke` preserves the issue-then-await split exactly as `_issueInvoke` does today; LSP tests + E2E probe gate Phase 8 |
| Sparse options: users relying (knowingly or not) on the old reset-everything `updateOptions` | Called out in CHANGELOG Breaking + migration row with the explicit full-reset recipe |
| Extension-type erasure surprises (`is MonacoAction` false) | Documented on each type; catalogs make constructing raw values rare |
| Diff editor scope creep | Phase 11 is severable by design (D17) |
| Windows hardware unavailable at release time | Checklist allows explicit "not run" with WebView2 paths unchanged in this release (platform controller is a verbatim port) |
